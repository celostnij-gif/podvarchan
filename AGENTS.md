# AGENTS.md — podvarchan.com

Этот файл — обязательный контекст для любого AI-агента (Claude Code, Cursor и т.д.), работающего
с этим репозиторием. Перед любой правкой агент обязан прочитать этот файл целиком. Если инструкция
в промпте пользователя противоречит этому файлу — приоритет у **AGENTS.md**, если явно не указано
обратное.

Это финализированная версия. Более ранние версии этого файла содержали неточности (описывали
кеш-архитектуру и расположение файлов так, как они были задуманы изначально, а не так, как они
были фактически реализованы и исправлены по ходу нескольких циклов отладки). Эта версия описывает
**фактическое** текущее состояние. Если агент находит в коде расхождение с этим файлом — см.
Раздел 10 («Семь раз отмерь») прежде чем действовать по любому из них.

## 0. Что это за проект

Двуязычный (RU/UK) сайт практикующего гипнотерапевта Вячеслава Подварчана с собственной
CMS-админкой. Ниша **YMYL** (Your Money Your Life — психологическая/медицинская тематика),
поэтому к SEO/E-E-A-T требования выше стандартных.

```
podvarchan/
├── src/                          # Public worker — podvarchan.com (READ-ONLY из D1)
├── apps/admin/src/                # Admin worker — admin.podvarchan.com (READ+WRITE D1/R2/KV)
├── packages/shared/src/db/schema/ # SOURCE OF TRUTH для схемы БД (Drizzle)
├── drizzle/migrations/            # SQL-миграции
├── messages/                      # i18n fallback (ru.json, uk.json)
├── scripts/                       # seed, revalidate, seo-regression и др.
└── TEMP/                          # Планы/аудиты/агентские промпты (рабочая область, не деплоится)
```

Два независимых Cloudflare Workers на **общей** D1-базе `podvarchan` и общей R2-медиатеке
`podvarchan-media`. KV разделён на два **независимых** namespace: `RATE_LIMIT_KV`
(rate-limit + скомпилированные `redirect_rules`) и `CONTENT_CACHE_KV` (кеш контента, префикс
ключей `d1c:`). R2 под кеш контента и ISR-кеш фреймворка — тоже разделены на независимые бакеты
(см. Раздел 3 — смешивание этих бакетов однажды уже было ошибкой и было исправлено).

**Возможен legacy-каталог `apps/site/`** — более старая версия публичного воркера, не упомянутая
в `.github/workflows/deploy.yml` и корневом `package.json`. CI её не деплоит, на прод она не
влияет. Если она всё ещё физически существует в репозитории на момент чтения этого файла — не
редактировать её код по ошибке вместо `src/`, и поднять вопрос об архивации/удалении с владельцем
(см. Раздел 11 — держать в репозитории неиспользуемый параллельный код противоречит принципу
«только живой код»).

## 1. Жёсткие технические ограничения Cloudflare Free Plan

Эти лимиты **не обсуждаются** и не решаются апгрейдом тарифа — вся архитектура обязана в них
укладываться.

| Ресурс | Лимит | Что это значит на практике |
|---|---|---|
| CPU time / запрос | **~10 мс** | Не wall-time — именно CPU. Превышение даёт `Error 1102`, необратимую платформенную ошибку, **не перехватываемую `try/catch`** (isolate обрывается принудительно). Любой тяжёлый синхронный код (парсинг больших JSON, ресайз изображений, сложные regex-цепочки в middleware, агрегация из нескольких источников без собственного кеша готового результата) — кандидат на превышение. Профилировать всё, что трогает middleware или рендер публичной страницы. |
| Bundle size / воркер | **~3 MiB gzip** | Публичный воркер и админка **разделены намеренно** — не сливать обратно в один проект. Тяжёлые клиентские библиотеки — только точечный импорт, тяжёлую анимацию — через `next/dynamic({ ssr: false })`. |
| D1 Reads | 5,000,000 / сутки | С запасом при текущем трафике, но публичные страницы всё равно обязаны идти через кеш-слой (Раздел 3), не бить в D1 при каждом запросе. |
| D1 Writes | 100,000 / сутки | С запасом — не плодить лишние `UPDATE` (не писать `updated_at` на чтение). |
| KV операций | 100,000 / сутки на namespace | Два раздельных namespace — не смешивать назначение. Неограниченные по кардинальности источники ключей (например, необработанные мусорные пути от бот-сканеров) — реальный вектор истощения квоты, отсекать их максимально рано, до похода в KV. |
| R2 Storage | 10 GB | Медиа + кеш-снапшоты контента + ISR-кеш фреймворка в раздельных бакетах. Загружаемые изображения — только WebP/AVIF, без хранения оригиналов в высоком разрешении без необходимости. |
| Workers requests | 100,000 / сутки на 2 воркера суммарно | Каждый внутренний cross-worker fetch — отдельный request budget. Не делать revalidate-запросы чаще необходимого. |
| Image resizing | **Недоступен в рантайме Workers** | Никаких `sharp`, `next/image` loader'ов с server-side resize, Cloudflare Image Resizing API в рантайме воркера. Ресайз/конвертация — **только** client-side в браузере админки при загрузке (`<canvas>`/`createImageBitmap`), не на сервере. |
| Cron Triggers | Доступны на Free Plan | Используются для прогрева кеша агрегатов (sitemap и т.п.) — см. Раздел 3. Экспортироваться должны строго определённым образом, см. платформенную особенность в Разделе 3. |

### Кодифицированные ограничения проекта (не менять без явного запроса владельца)
- Доступ к D1 **только** через `getRequestContext().env.DB`.
- `no any` в TypeScript (strict mode) — без исключений.
- Иконки из `lucide-react` — импортировать под алиасом `ImageIcon`, если это `Image` (конфликт с DOM/Next `Image`).
- **Server Actions существуют только в `apps/admin/src/lib/actions/**`.** Публичный воркер — read-only, никаких мутаций, никаких Server Actions на публичных страницах.
- Всегда держать в уме 10мс CPU-бюджет при написании любого кода, исполняемого на каждый публичный запрос (middleware, `generateMetadata`, layout, любой агрегирующий route handler).

## 2. Архитектурное правило: публичный сайт READ-ONLY

`src/` (podvarchan.com) не создаёт, не обновляет и не удаляет строки в D1 **никогда**, за одним
исключением — запись лида в `contact_leads`/`lead_events` через `/api/contact/` (единственный
легитимный write-путь с публичной стороны, обязательно с rate-limit через `RATE_LIMIT_KV` и
валидацией антибот-защиты).

Все остальные мутации — только через `admin.podvarchan.com`. Если задача требует, чтобы публичная
страница «что-то запомнила» — это либо KV-кеш (временное, невидимое пользователю), либо задача для
админки, а не для `src/`.

## 3. Обязательный контракт кеширования (три уровня + агрегаты)

Любая новая функция чтения данных в `src/lib/db/public.ts` **обязана** идти через кеш-обёртку
проекта, а не дёргать `env.DB` напрямую из компонента страницы. Название самой обёртки могло
поменяться между циклами разработки — **перед использованием проверить её актуальное имя и
сигнатуру прямым чтением файла `src/lib/db/public.ts` / `src/lib/cache/*`**, не полагаться на
конкретное имя функции, зафиксированное в более раннем документе.

### 3.1 Слои и порядок

```
CDN edge cache — Cache API воркера (caches.default), НЕ зонные Cache Rules Cloudflare
      ↓ miss
KV (CONTENT_CACHE_KV, префикс d1c:) — TTL по типу сущности, см. матрицу ниже
      ↓ miss
R2 (отдельный бакет под контент-кеш, НЕ тот же бакет, что incremental cache фреймворка) — durable fallback
      ↓ miss ИЛИ D1 недоступен
D1 (source of truth) — только тут разрешён прямой SELECT
```

**Важная платформенная особенность, зафиксированная эмпирически**: зонные Cache Rules Cloudflare
**не применяются** к ответам, которые генерирует сам Worker — это подтверждённое поведение
платформы, не баг конфигурации. Единственный рабочий способ кешировать ответы воркера на edge —
явный вызов Cache API (`caches.default.put`/`match`) из кода самого воркера. Не пытаться решить
проблему отсутствия edge-кеша через настройку зонных Cache Rules в Dashboard — это тупиковый путь,
уже пройденный и не сработавший.

**Вторая платформенная особенность**: Cloudflare Cache API **не сохраняет** ответы с заголовком
`Vary`, отличным от `Accept-Encoding` — `put()` в этом случае тихий no-op без ошибки. Next.js/RSC
по умолчанию ставит `Vary: rsc, next-router-state-tree, ...` на HTML-ответы. Кеширующая обёртка
обязана убирать `Vary` у **сохраняемой копии** (не у ответа, отдаваемого пользователю) и
ограничивать кеширование обычными навигационными запросами (не RSC/prefetch) — иначе edge-кеш
стабильно пуст без единой видимой ошибки в логах.

**Третья платформенная особенность**: `KV.put()`/`R2.put()`, вызванные без `await` и без передачи
в `ctx.waitUntil(...)`, могут не успеть выполниться до завершения запроса воркером. Любая запись
в фоновом режиме («fire-and-forget») обязана идти через `ctx.waitUntil(...)`, не голым вызовом без
ожидания.

### 3.2 R2-бакеты — назначение и разделение

R2 для кеша контента и R2 для incremental cache фреймворка (OpenNext/ISR) — **разные бакеты**.
Смешение их в одном бакете под общим биндингом уже было ошибкой в прошлом цикле разработки
(риск: внутренние ключи фреймворка и произвольные ключи кеш-обёртки в одном пространстве имён,
непредсказуемое поведение при апдейте фреймворка) и было исправлено выделением отдельного бакета
специально под контент-кеш проекта. Не объединять их обратно.

### 3.3 TTL-матрица (ориентир; актуальные точные ключи и TTL — сверить с `src/lib/cache/*` перед правкой)

| Сущность | Группа ключей (префикс `d1c:`) | TTL, ориентир |
|---|---|---|
| `navigation_items`, `site_settings`, `contact_channels` | `nav:*`, `settings:*`, `contacts:all` | 86400 |
| `services`, `service:{slug}`, `faq:{group}` | `services:*`, `service:{slug}:{locale}`, `faq:{group}:{locale}` | 21600 |
| `pages`, `blog_categories`, `testimonials` | `page:{type}:{locale}`, `blog-cats:{locale}`, `testimonials:*` | 43200 |
| `blog_posts` список/detail | `blog:list:{locale}`, `blog:{slug}:{locale}` | 3600 |
| `media_assets` (url/variants) | `media:url:{hash}`, `media:variants:{hash}` | по семейству, точечная инвалидация по id |
| `seo_meta` override | `seo:{entityType}:{id}:{locale}` | по семейству |
| Скомпилированные `redirect_rules` | ключ в `RATE_LIMIT_KV`, не в `CONTENT_CACHE_KV` | короткий TTL (десятки секунд) + инвалидация из админки |

Изменение TTL-матрицы — только с пересмотром всего плана инвалидации, не точечной правкой одного
числа без понимания, что ещё на него полагается.

### 3.4 Cache-Control (edge) по типам страниц — ориентир

| Тип страницы | `s-maxage` | `stale-while-revalidate` | `stale-if-error` |
|---|---|---|---|
| Home / Services / FAQ / About / Method / Pricing / Contacts / Privacy / Disclaimer | 604800 | 2592000 | 604800 |
| Blog (list/post/category) | 86400 | 604800 | 604800 |
| `/sitemap.xml`, `/robots.txt`, `/llms.txt`, `/llms-full.txt` | 3600 | 86400 | 604800 |
| `/api/preview/` | `no-cache, no-store, must-revalidate` | — | — |

### 3.5 Правило для агрегатов (sitemap, llms.txt, llms-full.txt, любой будущий сводный артефакт)

Любой артефакт, который строится из нескольких сущностей, обязан соответствовать трём требованиям
(нарушение этого правила уже один раз положило сайт мёртвой петлёй через `Error 1102`):

1. **Готовый артефакт кешируется целиком, не пересобирается на каждый запрос.** Отрисованный
   результат (XML/текст) лежит в `CONTENT_CACHE_KV` с зеркалом в R2 (без TTL в R2 — durable
   fallback). Путь запроса при тёплом кеше — один KV `get`, не серия кеш-лукапов + D1-запросов +
   сериализации.
2. **Сборка агрегата использует только лёгкие geттеры** (например, для sitemap — только
   `id`/`slug`/`updatedAt`/`publishedAt`, не полные объекты с тяжёлыми JSON-полями, нужными
   страницам, а не карте сайта). Запрещено строить агрегат из тех же тяжёлых списков, что грузят
   обычные страницы.
3. **Прогрев после инвалидации и по cron.** Инвалидация агрегата синхронно удаляет KV+R2 и
   немедленно ставит прогрев через `ctx.waitUntil`; плюс отдельный cron-прогрев держит KV тёплым
   до истечения TTL. Первый запрос после публикации должен быть KV-hit, не тяжёлый рендер в пик
   трафика. **Purge без последующего прогрева — незавершённая операция**: после деплоя,
   затрагивающего публичные шаблоны, точечный purge конкретных путей обязан сопровождаться
   немедленным GET-запросом к каждому из них (из CI), чтобы холодный рендер происходил во время
   деплоя, а не для первого реального посетителя.

**`sitemap.xml` реализован как обычный route handler (`route.ts`), не как файл Next.js-конвенции
`sitemap.ts`.** Причина: metadata-роуты Next.js рендерятся вне полноценного request-контекста
воркера, без надёжного доступа к D1 в рантайме, и получают собственные короткие дефолтные
Cache-Control заголовки. Не заменять route handler обратно на `sitemap.ts`/`robots.ts` файлы
Next.js-конвенции — это уже было опробовано и приводило к CPU-инцидентам.

### 3.6 Платформенная особенность cron-хендлера

`scheduled()`-хендлер обязан экспортироваться **только** как поле объектного литерала
default-экспорта воркера (`export default { fetch, scheduled }`), не как отдельный standalone
named export. esbuild собирает standalone named export `scheduled` в блок `export { ...,
scheduled }` в хвосте бандла, и workerd в этой форме классифицирует `scheduled` как класс Durable
Object, а не как cron-хендлер — cron падает с ошибкой «Handler does not export a scheduled()
function», хотя код физически присутствует в бандле и билд проходит без ошибок. После любого
рефакторинга entry-файла воркера — проверить через Cloudflare API метаданные задеплоенной версии:
поле `handlers` должно содержать `"scheduled"`, не только `named_handlers`.

## 4. Обязательная инвалидация кеша при любой мутации

**Каждая функция в `apps/admin/src/lib/actions/**`, вызывающая `db.insert/update/delete`, обязана
в конце вызвать инвалидацию точечных ключей, затронутых этой мутацией.** Без исключений. PR,
добавляющий новую server action с мутацией без вызова инвалидации, считается незавершённым.
Точное имя функции-обёртки (например, `revalidatePublic`/`invalidateContent`, могло измениться) —
проверить в `apps/admin/src/lib/revalidate.ts` перед использованием, не гадать по названию из
более раннего документа.

Инвалидация обязана:
1. Собирать точный список затронутых KV-ключей через существующие билдеры (не изобретать новый
   формат ключей и не делать widescale wipe по префиксу без крайней необходимости — точечное
   удаление, не `invalidateAll`/`purge_everything`).
2. Если список ключей превышает лимит одного batch-запроса к публичному воркеру (лимит существует
   и проверен — не убирать без замены) — **чанковать на несколько последовательных вызовов**, не
   молчаливо обрезать список (`slice(0, N)` без остатка — это класс бага, который уже один раз
   реально терял часть инвалидации при массовых правках).
3. Синхронно удалить соответствующие ключи из `CONTENT_CACHE_KV` **и** вызвать
   `revalidatePath()`/`revalidateTag()` Next.js **и**, если затронуты пути на edge-Cache API,
   инициировать их purge.
4. Не полагаться на истечение TTL как на основной механизм публикации — TTL это safety net, не
   рабочий путь обновления.

Если агент пишет новый server action и не уверен, как правильно собрать список ключей для
инвалидации — сначала прочитать существующие примеры в `apps/admin/src/lib/actions/`, не
изобретать новый паттерн.

## 5. SEO — обязательный чек-лист (на каждую новую/изменённую публичную страницу)

Ничто из перечисленного не опционально для YMYL-ниши психологии/гипнотерапии:

- [ ] `<title>` уникален, 50-60 символов, есть в обеих локалях (`ru`/`uk`).
- [ ] `<meta name="description">` 140-160 символов, уникален.
- [ ] `<link rel="canonical">` формируется через существующий хелпер построения canonical, никогда не хардкодится вручную.
- [ ] `hreflang`: `ru` + `uk` + `x-default` присутствуют на **каждой** странице — это неоднократно оказывалось источником регрессии на новых типах страниц, проверять особенно внимательно.
- [ ] Если UK-путь структурно отличается от RU-пути для той же сущности (проект уже проходил через переименование целых разделов каталога между локалями — например, услуги на UK-локали) — использовать единый источник маппинга (в идеале — производный от D1, не отдельная вручную поддерживаемая карта-константа, которая рано или поздно рассинхронизируется с БД), не создавать новый паттерн для каждой страницы.
- [ ] JSON-LD подключён **в серверном рендере страницы** (в исходном HTML, не только в клиентском состоянии/RSC-пейлоаде, регистрируемом после гидрации) и включает `dateModified` (из `updatedAt` сущности), не только `datePublished`. JSON-LD, добавленный только клиентски, невидим для краулеров без JS — это не соответствует требованию.
- [ ] Для YMYL-контента (тревога, паника, ПТСР, любая клиническая тематика) — блок `reviewedBy`/`medicallyReviewedBy` обязателен на новых статьях этой категории, без исключений, и тоже в серверном рендере.
- [ ] `robots` meta = `index, follow`, если явно не требуется иное (draft/preview — `noindex`).
- [ ] Open Graph (`og:title`, `og:description`, `og:image`, `og:url`, `og:type`, `og:site_name`, `og:locale`) и Twitter Card (`summary_large_image`) — присутствуют всегда, `og:image` минимум дефолтный, по возможности — конкретный для сущности, если задан через админку.
- [ ] Новая страница/сущность автоматически попадает в `sitemap.xml` через существующий route handler (Раздел 3.5), не через ручное добавление URL.
- [ ] Alt-тексты обязательны на всех `<img>`, в обеих локалях, WebP/AVIF формат, `width`/`height` заданы явно (избегать CLS).
- [ ] Single `<h1>` на страницу, логичная иерархия `<h2>`/`<h3>` без пропусков уровней.
- [ ] Никаких новых внутренних ссылок без описательного anchor text (не «нажмите сюда»).
- [ ] `AggregateRating` (если используется на странице) — только из реальных данных `testimonials`, никогда не хардкодить числа.
- [ ] После любой правки, затрагивающей >1 страницу — прогнать `scripts/seo-regression.sh`, должно быть зелено.

**Запрещено:** создавать страницу/сущность, у которой отсутствует хотя бы один из первых пяти
пунктов чек-листа выше (title/description/canonical/hreflang/UK-path-маппинг) — именно это было
причиной «нулевая индексация Google» в раннем аудите проекта.

## 6. AI-поиск / GEO (готовность для LLM и AI Overviews)

Публичный сайт должен одинаково хорошо отдаваться и человеку в браузере, и AI-агенту/краулеру.

- [ ] `robots.txt` разрешает `GPTBot`, `Google-Extended`, `ClaudeBot`, `CCBot`, `Applebot-Extended`, `Amazonbot`, `Bytespider`, `PerplexityBot`, `ChatGPT-User`, `CloudflareBrowserRenderingCrawler` — **не удалять и не сужать** этот список без явного запроса владельца.
- [ ] `Content-Signal: ai-train=yes, search=yes, ai-input=yes` header — сохраняется на всех ответах.
- [ ] `/llms.txt` и `/llms-full.txt` обновляются при добавлении новых типов услуг/крупных разделов — не статичный файл «на один раз», а живой артефакт (см. правило агрегатов, Раздел 3.5), синхронизированный с реальным составом сайта.
- [ ] `/api/md` (content negotiation `Accept: text/markdown`) обязан отдавать markdown-версию **любой** новой публичной страницы. Этот путь ранее был замечен в тяжёлых self-fetch/полном HTML-парсинге на горячем пути — при правке следить, чтобы он тоже соответствовал правилу агрегатов (Раздел 3.5), не тянул тяжёлые операции синхронно на каждый запрос.
- [ ] Контент новых страниц/статей должен следовать **BLUF** (bottom-line-up-front): первый абзац — прямой ответ на вопрос, без «воды» перед сутью.
- [ ] Предпочитать факт-плотный контент: списки, конкретные цифры (длительность сессии, формат, цена), а не общие описательные фразы.
- [ ] Structured data (`Person`, `ProfessionalService`, `Service`, `FAQPage`, `BlogPosting`, `BreadcrumbList`) — обязательны на соответствующих типах страниц, в серверном рендере (см. Раздел 5). **Не использовать `MedicalBusiness`/`HealthAndBeautyBusiness`** — эти типы подразумевают физическое медучреждение с адресом/часами приёма, что не соответствует формату онлайн-консультаций.
- [ ] `/api/mcp/` (MCP endpoint) — не ломать контракт при рефакторинге; новые MCP-инструменты документировать рядом с их реализацией.
- [ ] `/.well-known/security.txt` (RFC 9116) — не удалять, обновлять контакт при смене владельца/email.

## 7. Что нельзя делать никогда (hard no)

- Мержить `src/` (public) и `apps/admin/src/` (admin) обратно в один Next.js проект/воркер.
- Использовать `sharp` или любой server-side image resize в рантайме Workers.
- Ставить `revalidate`/TTL короче необходимого «для перестраховки» — увеличивает нагрузку без пользы, раз on-demand-инвалидация работает.
- Делать прямой `env.DB.select()` из компонента публичной страницы, минуя кеш-обёртку.
- Добавлять мутацию в админке без парного вызова инвалидации.
- Хардкодить SEO-данные (title/description/canonical/цены/credentials, если для них уже есть или должна быть колонка в D1) в JSX/константах/`messages/` вместо чтения из D1 через существующий read-path. Это уже один раз потребовало полного отката целого цикла работы.
- Урезать список разрешённых AI-ботов в `robots.txt` или `Content-Signal` header без явного запроса от владельца.
- Публиковать новую YMYL-статью без `reviewedBy`/`medicallyReviewedBy` в серверном рендере.
- Удалять/переименовывать колонки в `packages/shared/src/db/schema/` без миграции и без прямой проверки заполнения в живой D1 — отчёты в `TEMP/` могут быть устаревшими, никогда не источник истины сами по себе (см. Раздел 10).
- Запускать `npx wrangler deploy` вручную локально вместо push в `master` (деплой идёт через CI/GitHub Actions).
- Пытаться чинить отсутствие edge-кеша через зонные Cache Rules Cloudflare Dashboard — не работает для ответов воркера (Раздел 3.1).
- Регулярный `purge_everything`/wipe всего KV-namespace как основной механизм инвалидации.
- Оставлять в кодовой базе два параллельных механизма для одной и той же задачи «на всякий случай» (старая и новая версия функции, старый и новый route одновременно, закомментированный код) — см. Раздел 11.
- Принимать структурное решение (смена URL-схемы, схема БД, состав ролей, редизайн ключевого потока) по факту наличия незакоммиченного/неполного кода в рабочей копии без явного подтверждения владельца, что это осознанное решение, а не случайный артефакт прошлой сессии.

## 9. Definition of Done для любой задачи агента

Задача не считается завершённой, пока не выполнено всё применимое из списка:

1. Код проходит `no any` / strict TypeScript без ошибок.
2. Если тронут `src/lib/db/public.ts` — чтение идёт через актуальную кеш-обёртку (Раздел 3), не напрямую.
3. Если тронута любая admin server action с мутацией — добавлен вызов инвалидации (Раздел 4), с чанкованием при большом числе ключей.
4. Если добавлена/изменена публичная страница — пройден чек-лист SEO (Раздел 5) и AI-готовности (Раздел 6), включая проверку, что JSON-LD реально в серверном HTML, а не только в клиентском состоянии (curl без исполнения JS).
5. `scripts/seo-regression.sh` зелёный.
6. Bundle budget не превышен ни у одного из двух воркеров.
7. Изменение подтверждено **живой проверкой**, не только чтением кода (Раздел 10) — там, где применимо: `curl` на реальный URL, реальный SQL-запрос к прод-D1, реальный клик в UI админки, а не «код выглядит правильно».
8. Не оставлено дублирующего/мёртвого кода после правки (Раздел 11) — если задача заменяла механизм, старый вариант удалён в том же PR, не оставлен «на всякий случай».
9. Изменения задокументированы одним markdown-файлом в `TEMP/` (если это часть плановой задачи), с явной пометкой даты и статуса каждого закрытого пункта — с фактом-доказательством, не декларацией.

## 10. «Семь раз отмерь» — обязательная проверка перед любой правкой

Это не рекомендация, а обязательный шаг перед внесением изменений, особенно если задача основана
на выводах из `TEMP/`-отчёта, более раннего сообщения в диалоге, или памяти о том, «как это должно
быть устроено». История проекта содержит несколько эпизодов, когда действия по неподтверждённым
выводам приводили к повторной поломке уже исправленного, отмене чужой работы или трате цикла на
несуществующую проблему.

**Правило:** прежде чем менять код на основании любого утверждения о текущем состоянии проекта
(«баг X существует», «фича Y уже реализована», «поле Z не используется», «показатель N равен
такому-то») — подтвердить это утверждение самостоятельно, одним из способов ниже, и только потом
действовать:

1. **Про код** — открыть реальный файл и прочитать его целиком в актуальном состоянии, не
   доверять описанию «что там написано» из отчёта, каким бы недавним он ни казался. Файлы могли
   измениться между написанием отчёта и текущим моментом.
2. **Про БД** — прямой `SELECT`/`COUNT`/`GROUP BY` к продовой D1 (или локальной копии схемы, если
   речь о структуре, не о данных). Никогда не доверять числам из старого markdown-отчёта как
   источнику истины — в истории проекта многократно фиксировались случаи, когда разные отчёты
   одной и той же датой противоречили друг другу по количеству строк/значениям.
3. **Про публичный сайт** — реальный `curl`/HTTP-запрос к живому URL (заголовки, статус-код, тело
   ответа), не предположение по коду о том, как он должен отвечать. Кеш-слои, конфигурация
   инфраструктуры и рантайм-поведение платформы (см. платформенные особенности в Разделе 3)
   регулярно расходятся с тем, что «должно быть» по чтению одного лишь кода.
4. **Про админку** — реальное действие в UI (создать/изменить/удалить тестовую сущность с
   маркировкой) и проверка результата, а не предположение, что server action, который выглядит
   правильно, реально сохраняет то, что должен.
5. **При двух противоречащих источниках** (два отчёта, отчёт vs код, старая версия AGENTS.md vs
   найденное в коде) — не выбирать, какому верить, «на глаз». Проверить фактом (пп. 1-4) и
   зафиксировать, какой источник оказался устаревшим, явно, в итоговом отчёте задачи — чтобы
   следующий цикл не наступил на то же противоречие.

**Особый случай — незакоммиченные/uncommitted/untracked изменения в рабочей копии.** Если агент
обнаруживает в рабочей директории код, который не является частью текущей задачи, не
закоммичен, и по масштабу — не мелкая правка (переименование route-сегмента, изменение схемы
данных, смена ключевого потока) — это не повод ни продолжать работу поверх него как ни в чём не
бывало, ни откатывать его без разбора. Правильное действие: остановиться на этом конкретном
вопросе, кратко описать находку, и явно спросить владельца, является ли это осознанным,
незавершённым решением (тогда продолжить обдуманно) или случайным артефактом (тогда откатить).
Не гадать самостоятельно.

## 11. Только живой код — без рудиментарных ответвлений

Цель — быстрый, чистый, поддерживаемый код, без нагромождения параллельных механизмов,
оставленных «на всякий случай» от прошлых циклов правок.

- **При замене механизма — удалять старый в том же PR.** Если задача заменяет способ чтения
  slug'а, генерации JSON-LD, инвалидации кеша и т.п. на новый — старая реализация не остаётся
  рядом «на случай, если новая не заработает». Если нужна подстраховка на время проверки —
  использовать git-историю (откат коммитом), не два одновременно живых пути в коде.
- **Не создавать вторую версию источника данных**, если уже есть один канонический (частый
  паттерн в истории этого проекта: хардкод-константа рядом с колонкой D1, которая должна быть
  единственным источником истины — оба существуют, со временем расходятся, непонятно, какой
  «главный»). Если по архитектурным причинам нужен fallback на случай недоступности основного
  источника — он должен быть автоматически производным от основного (генерироваться из него),
  а не поддерживаться отдельно вручную.
- **Не оставлять закомментированный код** «вдруг пригодится» — если он не нужен прямо сейчас, его
  можно найти в git-истории при необходимости.
- **Встретив при работе явно неиспользуемый код** (мёртвый экспорт, файл, на который никто не
  ссылается, конфигурация для функции, которая больше не вызывается) — не обходить его молча.
  Если удаление в рамках текущей задачи безопасно и очевидно — удалить. Если неочевидно (может
  использоваться иначе, чем показал grep, или решение о судьбе требует владельца — см. пример
  `apps/site/` в Разделе 0) — явно зафиксировать находку в отчёте задачи как открытый вопрос, не
  игнорировать.
- **Не плодить временные/тестовые файлы-заметки в TEMP/ без необходимости.** Один документ на
  задачу/цикл, с чёткой датой в названии; если работа над одной темой продолжается несколько
  сессий подряд — обновлять существующий файл, а не создавать `_v2`, `_v3`, `_final`,
  `_final_v2` без разбора — это уже само по себе создало путаницу в прошлом (архив содержал
  десятки частично устаревших отчётов, требующих отдельного разбора, что каждое из них ещё
  актуально). Периодически — предлагать владельцу свернуть устаревшие отчёты в один актуальный
  документ вместо накопления.
